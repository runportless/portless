# ADR 0001: one machine-local daemon

Status: accepted

Portless uses one lazily started daemon per user account. It centrally allocates ports, serves the control plane and application ingress through a private Unix socket, coordinates projects, and keeps the UI alive independently from any one CLI invocation.

A per-project daemon would make two checkouts race for control ports and would duplicate the gateway. The CLI therefore starts the user daemon on demand under a startup lock and discovers its private control port through a mode-0600 record inside a mode-0700 user-owned directory.

The discovery record is not sufficient proof of identity. Every API-using CLI invocation authenticates a fixed lifecycle endpoint with the private CLI token and compares the response with both the record and local installation state. The handshake binds together:

- a fingerprint derived from the installation ownership key;
- a random instance fingerprint generated for each daemon start;
- the daemon PID and start time;
- lifecycle and application API protocol versions; and
- a SHA-256 fingerprint of the executable that started the daemon.

This catches stale development daemons even when their coarse API version has not changed. It also prevents a healthy process listening on the recorded port, a reused PID, or an edited record from being treated as the daemon. The private identity and shutdown routes require CLI bearer authentication and are not served on application hosts or available to browser sessions. The control API separately exposes browser-safe daemon status and guarded restart routes; browser mutations still require the session CSRF token and same-origin checks.

Authenticated daemon identity and public daemon status are deliberately shallow: they report process, build, recovery, and active-environment state without probing every managed runtime. Handoff readiness is a separate authenticated operation that checks supervisors, containers, proxy listeners, and current ownership with bounded concurrency. The control plane requests it when the daemon drawer opens, and `portless daemon status` requests it explicitly for operator diagnostics. An authenticated older build is replaced automatically when there are no active environments or a fresh audit proves every managed runtime can be handed off safely. Explicit `portless daemon stop`, `portless daemon restart`, and ordinary UI restart repeat the audit immediately before replacement and fail closed if ownership cannot be proven. When a fresh browser audit specifically reports a blocked handoff, the drawer exposes a distinct force restart behind a second explicit confirmation that names every active environment and warns that runtimes may be interrupted or need to be started again. The server accepts this bypass only from a same-origin browser session with a valid CSRF token; it still verifies the exact daemon instance and reads the active-environment inventory before replacing the process. CLI `--force` may also interrupt active environments and can replace a legacy daemon after additionally checking process ownership and command arguments. Raw PID signaling is never the normal control path.

Normal CLI, browser, MCP, on-disk executable-change, and browser force triggers converge on a single in-process replacement coordinator. Concurrent triggers reuse one restart receipt and commit one `exec` replacement; the receipt records whether runtime handoff safety was confirmed. The API flushes that receipt before replacement begins; shutdown then cancels all request contexts so SSE and other long-lived handlers cannot consume the drain budget, bounds HTTP draining and application cleanup, and carries the receipt into the new process. A replacement is complete only when a different current-build instance publishes ready state. In-process callers use a fixed five-second end-to-end deadline with an operational target below two seconds, while diagnostics retain the most recent duration and SLA result. Legacy forced stop/start recovery is intentionally excluded from this deadline.

Browser sessions are retained in a mode-0600 session record under the user's private Portless directory. That lets an authenticated control-plane tab reconnect after an in-process daemon replacement while preserving server-side expiry and logout revocation.

Clean HTTP URLs and conventional TCP ports require privileged loopback setup. `portless setup` is the first-run shortcut for `portless relay install`; both install one deliberately narrow system service that binds `127.0.0.1:80` and UDP/TCP `127.77.0.1:1053`, immediately drops to the installing user's UID/GID, and forwards bytes to that user's separate mode-0600 HTTP and DNS daemon sockets. A fixed root-owned machine lock serializes privileged installation, repair, restart, and removal from the final ownership inspection through verification. Installation and repair are transactional across the helper, service, resolver, and ownership receipt, restoring the previous artifacts and service state when activation or bounded end-to-end HTTP, DNS, and system-resolver readiness fails. Atomic artifact replacement syncs file data, metadata, and containing directories before activation. The root-owned receipt is the only ownership authority: the relay process refuses to start unless its UID, GID, HTTP socket, DNS socket, and current loopback manifest exactly match that receipt, while deterministic service and resolver content is inspected separately for drift and is never an ownership fallback. macOS aliases may be adopted or removed only when listed in that validated receipt. Forced artifact cleanup without a valid receipt leaves unverified aliases untouched, reports the residual pool, and requires explicit operator verification instead of claiming complete removal. The scoped resolver uses the dedicated high DNS port instead of competing with a system-owned port-53 listener. On macOS the same installation provisions a bounded, reserved `127.77.0.x` alias pool on `lo0` and a resolver client for descendant `localhost` names; Linux already treats `127/8` as bindable loopback and `systemd-resolved` synthesizes those localhost records. The relay returns the protocol-defined loopback answer for every name in the special-use `localhost` zone even while the user daemon is unavailable. Dynamic `portless.test` queries are forwarded to the daemon and answered only from its durable endpoint-allocation table; names outside those two narrow zones are refused, so the relay does not become a general DNS forwarder. Discovery, orchestration, state, authentication, routing, and the UI remain in the unprivileged daemon. Ongoing inspection, restart, and removal use the explicit `portless relay` command group.

The relay source mirrors that privilege boundary. The `portless-relay` root is
private-command composition only; `runtime` owns listener binding, privilege
drop, and HTTP/DNS forwarding; `health` owns bounded probes and readiness; and
`installation` owns receipts, artifact transactions, lifecycle locking,
platform services, inspection, and removal. Dependency direction is
`installation -> health -> runtime`, with installation also allowed to use
runtime identities directly. Runtime never depends on lifecycle or health.

Full installation removal is a separate top-level lifecycle because application reset intentionally preserves installation identity and restarts an empty daemon. `portless uninstall` is non-mutating until explicit confirmation. Confirmed removal first authenticates and purges every recorded process/container runtime, then removes the current user's machine-wide relay while its ownership receipt and CLI helper remain available, stops the authenticated daemon under the startup lock without replacement, atomically detaches and deletes the validated user-owned data root, and removes only a verified installed CLI launcher. Each boundary stops later steps on failure. Full uninstall never inherits the relay-only ownership override, and it preserves an executable target when the launcher is a development symlink.
